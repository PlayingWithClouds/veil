# Veil

Self-hosted adult media library, single user. Go backend + SvelteKit frontend in a Bun monorepo, plugin-based scrapers. The backend is self-contained (in-process SQLite + blobs on disk) so it can run on a server or embedded in a phone app.

## Git

Work happens on `main`. No branches, no PRs. Deferred work goes into GitHub issues on `PlayingWithClouds/veil`, created with `gh` as the `PlayingWithClouds` account (check `gh auth status`; switch with `gh auth switch` if another account is active).

Commit the worktree first if it's dirty, then write your changes. Commit after every big change and push if a remote is configured. Short, to-the-point commit title; a body explaining the change when the title doesn't carry it; ask if you're unsure what to write. Always say the commit was made by you, not a human.

No trailers, ever: no `Co-Authored-By`.

## Entity model

Flat tags, no hierarchy.

- **scene** — atomic unit: one video. No series/season/episode; episodic content is a collection. Carries a studio link, performers + tags, preview assets, streams.
- **gallery** — image set; parallels scene for stills.
- **image** — one row per image. `content = true` rows (gallery pages, standalone images) are browsable/taggable/collectible; `content = false` rows are assets (posters, logos, profile shots).
- **performer** — bio + `aliases`, `tags`.
- **studio** — `aliases`, `tags`, `parent` link (network → studio hierarchy), `source_url` identity.
- **collection** — ordered members of any entity type (scene/gallery/image/performer/studio), no nesting. `user_created` = user playlist; otherwise scraper-created (site series, DVD; `created_by`/`source_url`).
- **tag** — flat; `aliases` merge synonyms at ingest.
- **scene_marker** — tag and/or label at `seconds` (optional `end_seconds` span). `personal` = user-created; otherwise global (e.g. plugin position tagger, `created_by`).

Tag search is inherited: `scenes(tagId)` matches the scene's own tags OR its studio's OR any credited performer's, ranked direct-first and surfaced as `tagMatch: "direct" | "inherited"`. Same for galleries/images (images also inherit via their owning gallery).

## Data rules

- Results from a fetch never expose the raw record ID structure — only ever `..._id: string`.
- Discovery is search-driven: search/browse results are ingested as stubs only (listing fields, no scrape). A scene's detail page is fetched once, when it is first visited (`ensureSceneStreams` → `Orchestrator.VisitScene`, tracked by `scene.detail_fetched_at`). That fetch also links the site's related videos (`scene_related`, source `site`); below 24 related, background fallback searches by performer, tag, then title fill the rest on the origin plugin. A gallery's page is fetched on open while it has no images (`ensureGalleryImages` → `Orchestrator.VisitGallery`).
- Subscriptions (`search_subscription`, `kind` = search | studio | performer | tag) re-run every `interval_hours`. Searches go through the same discovery path as live search. Studio/performer/tag subscriptions list the entity's site page via `scene:list:page` when a plugin supports it, else keyword-search the name on its origin plugins (keeping only scenes credited to it or not yet credited), and always add library scenes credited to it. Results collect in `search_subscription_item`; the first run's results count as seen, later arrivals as new.
- Ingest is observation-first: raw plugin payloads land in `observation`, merge into canonical records by identity (source_url → external_id → name), per-field history in `changes`.
- Same thing, several records: performers, studios and tags match by spelling-insensitive `name_key` (`internal/names`), and `RepairNamedRecords` merges the ones that predate it at startup. Scenes (`alike.SameSceneStrict`), galleries (`alike.SameGallery`) and scraper collections (same name + a shared member) are merged by `MergeDuplicateMedia` at startup and, for a newly created scene or gallery, at ingest. A merged-away record's `source_url`/`external_id` stay in `entity_identity` and resolve to the survivor. Merges are irreversible, so the matchers stay strict; the feed's `dropDuplicates` uses the looser `SameScene` and only hides.
- Stage names: `Orchestrator.ProfilePerformers` (start + every 6 h, 100 per run) searches the `freeones` plugin for performers without a profile and ingests the page that names them; its aliases are absorbed and any other performer whose name is one of them (full names only, two words or more) is merged in (`mergeAliasTwins`, also run by the startup repair). `mergeRecords(survivorId, mergedId)` merges two records by hand (web: ⋮ → "Merge into…" on performer/studio pages, a button on tag pages).
- Migrations are append-only (`db.Open` applies them and tracks versions in `_migration`); never edit an applied migration, add a new numbered file.
- Lists of links (`tags`, `performers`, `aliases`) are JSON columns; match them with `json_each`. Bind lists as `$param` and use `IN (SELECT value FROM json_each($param))`.

## Search

`/api/search` (SSE) sends library matches first, then each plugin's results as they arrive. The library part is an FTS5 index (`scene_search`, migration 030, trigger-maintained) over title + performer, studio and tag names ordered by bm25, with a title-substring fill (`ingest.SearchLibrary`); performers, studios, tags and galleries rank exact, prefix, word-prefix, substring (`media.searchOrder`). Every result event carries a `score` (`internal/searchrank`): text match + reciprocal-rank-fused place in its site list (library bm25 order counts as a list) + a small quality term (site rating, log view count) + a small taste term from `recommend.Engine.Profile`. Copies of one video on several sites (`alike.SameScene`, or the same record) collapse: a later copy is dropped unless it scores better, then it is sent with `replaces` (the old copy's source URL). The streaming order is arrival order, so clients sort by `score`: the web search page holds the first second of results, sorts them, and sorts later arrivals in below the first 12 (`src/lib/searchOrder.ts`), with a Relevance / Newest / Most viewed / Rating / Duration switch. The Android app and the other `pluginSearchStream` users still render in arrival order and ignore `score` and `replaces`.

`score = 3.0·text + 1.5·fusedRank·pluginShare + 0.4·(quality−0.5) + personalWeight·taste + 2.0·entity + 1.2·clickMemory` (`searchrank/weights.go`).

- **Entities in the query**: `searchrank.EntityIndex` (performer, studio and tag names, then aliases, by `names.Key`, cached 2 min, longest match first; a one-word performer name only when it is the whole query; a near-miss spelling of a 6+ letter name is a `fuzzy` match) links query spans to records. The `matched` SSE event lists them (`kind, id, name, alias?, fuzzy?`, plus `rewritten`); the web page shows chips linking to the entity. Scenes credited to a recognised entity score the entity credit (a stub without credits gets 0.7 for a title naming it; a scene listed on the entity's own page counts as credited). Up to 2 exactly spelled performers/studios (a tag only when it is the whole query) also have their site page listed through `scene:list:page` (`updater.Scheduler.PagePlugins`, `discovery.ListPage`) as one more rank list beside the keyword search.
- **Typos and synonyms**: a query word within 1 (4–7 letters) or 2 (8+) edits of a field word (same first letter) earns 0.6 of the whole-word credit, so exact matches stay ahead. When fewer than 5 exact library scenes match, `scene_search_fuzzy` (FTS5 trigram, migration 033) supplies candidates kept at text match ≥ 0.4. A query that used an alias or a near-miss spelling also runs as a `rewritten` query on the library and every plugin; its text counts 0.92.
- **Taste by specificity**: `searchrank.Specificity` (word count, share of words covered by a performer/studio or by tags, library match count) sets the taste weight from 0.6 (broad, "anal") down to 0.075 (title-like).
- **Learning from clicks**: the web search page logs the top 24 results as shown once the list has stayed put 2.5 s, and clicks, through `recordImpressions` with surface `search` and `query` (`src/lib/searchLog.ts`); the resolver files them in `search_event` (kept 90 days). `searchrank.History` turns them into a per-(query, scene) click memory (30-day half-life, similar queries by word Jaccard) and per-plugin rank-share factors in [0.5, 1.5] from smoothed click rates of the query's words. A remembered scene is only boosted when the search returns it. Android search logs nothing yet.

## Recommendations

`internal/recommend` runs candidate generation → ranking → re-ranking per request, no ML or external calls.

- **Signals** (per scene, time-decayed with a 30-day half-life): o-event (5) > session-ending watch (4: at least a minute played and no other scene started or played within 30 min after, finished or not, since a video that ends the session did its job) > like > save (watchlist, user collection) ≈ A/B pick > a watch another video followed (in full 1, partial 0.5; a watch less than 30 min old counts as followed) ≈ click (first visit or logged click); sessions come from `watch_history` started/updated times (`session.go`); negative: dislike, early abandon (played <10 s, or <5% of the runtime and <1 min), A/B reject, shown-but-not-clicked (`recommendation_impression`). Blocked entities pin to −1. Watches are judged by time played, not by the position reached, since viewers skip around: `watch_history.played_seconds` sums the gaps between the players' 15 s progress saves (web and Android save on playing time; a save more than 45 s after the last starts a new sitting and counts at most 15 s), and 5 min or 80% of the runtime played is a watch in full. A fresh followed watch plus its click seeds related scenes (`seedMinimumWeight` 0.9).
- **Profile**: computed on demand (no cache table to invalidate); signalled scenes spread their weight onto performers, tags (÷√count), studio and site (first observing plugin), each dimension normalized to [−1, 1].
  - **Tag rarity**: tags are weighted by log inverse share of tagged scenes (1 at ≤5%, floor 0.05; all 1 below 50 tagged scenes) when the profile spreads weight and in `tagAffinity`; blocked tags keep full weight. `libraryStats` (tag counts, performer attributes) is cached 10 min (`rarity.go`).
  - **Moments** (`moments.go`): for the 100 most recent session-ending scenes, the tags of `scene_marker` rows from 120 s before to 20 s after the stop point (`watch_history.progress_seconds`), and around the `scene_heat` peak (busiest bucket ≥ 2× the average, ±30 s), get an extra 0.5× share of the scene's weight in `profile.Tags`.
  - **Runtime** (`runtime.go`): signals (except shown-but-not-clicked) spread over six log-spaced runtime bands (3, 6, 12, 25, 50, 90 min), shrunk by `runtimeMinMass`; matched with weight 0.10 (match weights performer 0.36, tag 0.27, studio 0.18, site 0.09, runtime 0.10), neutral for an unknown runtime.
  - **Performer looks** (`attributes.go`): `Profile.Attributes` holds affinities per attribute (hair, ethnicity, eyes, country, natural/fake, tattoos, piercings, cup and height band) from rated performers. A performer with no affinity of their own inherits 0.5× the mean of their attributes' affinities (`castAffinity`).
- **Candidate sources**, each item tagged with one: `scene_related` of the strongest signalled scenes (site-related highest prior), new search-subscription finds, newest scenes of top performers/studios/tags, the feeder's finds (`discover:taste`, `discover:catalog`, `discover:popular`, `explore:site`), exploration from the library (random scenes of tags adjacent to the top tags, plus random), unvisited stubs from recent searches, newest scenes. Also `related:walk` (`walk.go`, personal, prior 0.5): a 3-hop personalized walk from the seeds over `scene_related` (forward, reverse ×0.5) plus shared-performer and shared-rare-tag edges, frontier ≤ 100 scenes per hop, proposing only scenes the direct related lists don't; and `explore:attribute` (exploration, prior 0.35): the newest scenes of up to 8 unknown performers with inherited looks affinity ≥ 0.15. Cold start = catalog finds, searches, newest.
- **Feeder** (`updater.Feeder`): the engine only ranks what is stored, so the feeder keeps it supplied without a search. Every 12 h (and when a ranking has fewer than 100 unwatched, unshown candidates, at most hourly) it lists one catalog page of every scene plugin (one page deeper per run, three deep) and the site pages, else name searches, of the top 3 performers, 2 studios and 3 tags (`taste`) and of 3 random adjacent tags (`explore`, so exploration draws on the sites, not only on the stored library), plus 2 most-viewed pages taking turns through `defaultPopularPages` (`popular`, entity = host; no plugin capability asks for "popular", so these are site URLs listed through `scene:list:page`, today kvs sites only, eporner's page listing would need a plugin change for its best-videos page), ingests them as stubs and records them in `feed_discovery` (kept 30 days, counted 14, at most 20 taste / 30 explore / 40 popular and catalog scenes per entity). A taste find's prior is scaled by the entity's current affinity down to a floor of half (`tasteAffinityFloor`), so a thin profile does not sink it below the catalog. A run that stored anything clears the memoized feed.
- **Ranking**: affinity match + source prior + freshness + site popularity − watched/fatigue/disliked-neighbour penalties. Popularity is the scene's view-count percentile among its site's scenes (first observing plugin) blended 70/30 with its rating percentile, neutral 0.5 when the site gave neither or has fewer than 20 samples; it mostly separates candidates the profile has no opinion on. A session-ending scene keeps the watched penalty for 3 days, then loses it linearly over 11 days and ends with a +0.3 bonus (`rewatch.go`); a watch another video followed keeps it. Blocked scenes, disliked scenes and inactive-plugin stubs are excluded. **Re-ranking**: each 24-slot page is shared out by source kind (`kindQuotas` in `weights.go`: personal = `related:*`/`affinity:*`/subscription 8, taste 5, catalog = catalog + popular 5, exploration = `explore:*` 4, search 2; newest is filler), the kinds spread over the page (a kind runs at most 2 slots ahead of an even spread) and ordered by score within; slots a kind cannot fill go to the best remaining items overall, search beyond its 2 last. Per-page caps per performer/studio/site (plugin) and no source or site three in a row still apply; the old every-7th-slot exploration rule is gone.
- **Learned priors and quotas** (`learning.go`, tunables in `weights.go`): per ranking, one SQL aggregation counts each source's showings (`recommendation_impression` kind `shown`, last 60 days, decayed with `AffinityHalfLife`, showings younger than 6 h skipped) and their rewards. A showing is opened when a logged click or a first visit (`scene.detail_fetched_at`) follows within 6 h and no later showing of the scene came in between (that one gets the credit); reward 0.6 when opened, +0.25 for a session-ending watch and +0.25 for a like within 7 days, capped at 1. Each source gets a Beta posterior centred on the pooled reward rate with 30 pseudo-rewards of prior strength (`learnPriorClicks`), so a source with little data stays at its hand-set prior. Thompson sampling draws once per ranking (`Engine.random`, injectable); the draw relative to the pooled rate, clamped to [0.5, 1.5], multiplies the source's `sourcePriors` value in `score`. The kinds are sampled the same way and shift `kindQuotas` (each between `kindQuotaMinimums` and 1.5x its default, summing to `pageSize`; `allocateQuotas`). Below 300 decayed showings nothing is learned. The learned values are logged at most every 30 min. Only the recommendation surfaces (`recommendationSurfaces` in `impressions.go`: home, legacy `feed` and empty, `row`, `preview-feed`) feed the learning and the shown-but-ignored signal and fatigue; on the other surfaces the user chose the page or query. Position bias: rewards are divided by a per-surface examination propensity per position bucket (`examination.go`), fitted from the logged positions and shrunk toward a decaying prior; showings without a position take the surface's mean.
- **Cross-site duplicates**: after scoring, `dropDuplicates` keeps the best-ranked copy of a video several sites carry (`alike.SameScene`: runtimes within 5 %, then identical credited performers or near-identical title; scenes without a runtime never match). `recommendations(excludeTagIds)` drops scenes carrying a tag (own, studio's or performer's) from the shared ranking, `scenes(includeTagIds, excludeTagIds)` does the same for listings, and `tasteProfile` exposes the profile's strongest liked and disliked tags, performers, studios and sites.
- **Watch again**: `Rows` adds a row (key `rewatch`, source `rewatch`, second position) of session enders last watched 7+ days ago, strongest first. It is a row only, never a feed candidate.
- The ranked feed is memoized 30 min for `offset > 0` so pages stay stable; `offset 0` re-ranks once the ranking is 10 min old, or on `refresh: true` (Home's refresh button).
- **Impressions**: every showing is logged with its `surface` and 0-based `position`: `home`, `row` (Home shelves, position within the row), `preview-feed`, `related` (the scene page's up-next list), `performer`, `studio`, `tag`, `search`. Web: `src/lib/recommendations.ts` (`use:impression={{ mediaId, surface, position, source? }}`, `recordClicked` with the same fields, `resetShownImpressions(surface)` when a list is replaced; batched through `recordImpressions`). Android: `data/ImpressionLogger` and `ui/components/ImpressionTracking.kt` (`LogShownScenes`, `logSceneClicked`).
- **Offline evaluation**: `go run ./cmd/recommend-eval -db path/to/veil.db` (in `apps/backend`; `-variants default,no-learning,baseline-newest,baseline-random`, `-window-days`, `-step-days`, `-repeats`, `-json`) works on a `VACUUM INTO` copy. Per cutoff it cuts the state back to then (events, stubs, related links, the tags and performers visits gave), ranks with the real engine (`recommend.NewWithOptions`) and scores the list against the next window: hit rate and recall at 24/96 and MRR for session-ending watches, watches and clicks, plus site/tag coverage and source shares. Targets created after the cutoff count as unreachable. Tables without timestamps are taken as they are now.

## Plugin system

Plugins are TypeScript packages under `apps/backend/plugins/`, all importing `@playingwithclouds/veil-sdk` (`runPlugin` dispatcher + shared types). The backend never runs their source: `scripts/bundle-plugins.ts` bundles each into one CommonJS file in `DATA_DIR/plugins/<name>/plugin.js` (the installed-plugins folder, same on server and phone), and the backend runs it in an embedded JS engine (goja, `internal/plugins/embedded*.go`), a fresh runtime per invocation, hot-reloaded via fsnotify. `bun dev` runs the bundler in watch mode, so saving a plugin file reloads it within a second.

**Distribution via GitHub, never npm:** plugins are assets of this repository's rolling `plugins` release: per version an npm-style tarball `<folder>-<version>.tgz` (`package/package.json` + `package/plugin.js`, keyword `veil-plugin`), plus `index.json` listing every package's latest version with tarball URL and sha512 integrity. Packages are named `@playingwithclouds/veil-plugin-<name>`; the folder name is the package name minus scope and `veil-plugin-`. `internal/pluginstore` reads the index (`DefaultIndex`, override with `PLUGIN_INDEX`), installs packages (integrity checked), installs the default set on a fresh backend, updates to newer versions at start and every 6 h, and seeds from `PLUGIN_SEED_DIR` (the phone app's bundled set) without undoing updates or uninstalls (`.store.json` in the plugin folder). Dev bundles carry `localBuild: true` and are never replaced. To ship a fix: bump `version` in the plugin's `package.json` (meta reads it from there), then `bun scripts/publish-plugins.ts [plugin …]` in `apps/backend` (needs `gh` logged in as PlayingWithClouds; `--dry-run` to preview; skips versions already in the index; uploads `index.json` last). Every backend picks it up within 6 h or on "Check for updates" in Plugins; the phone checks on every launch.

**Runtime rules** (what a plugin may use): web APIs (`fetch`, `URL`, `URLSearchParams`, `AbortSignal.timeout`, `JSON`, promises), the SDK, and pure-JS npm packages (the bundler inlines them). No Node/Bun built-ins, files, processes or native addons. `node-html-parser` is special: bundles keep it external and the backend answers `parse()` natively in Go (x/net/html + cascadia), because parsing in JS under goja is ~60× slower. Only `querySelector(All)`, `getAttribute`/`hasAttribute`, `closest`, `text`/`rawText`, `innerHTML`/`outerHTML`/`toString`, `tagName`, `id`, `classList` and `parentNode` exist there (`embedded_html.go`); add to it before relying on anything else. `bun test` in a plugin still runs the real node-html-parser, so check changed parsing against the embedded runtime: `bun scripts/bundle-plugins.ts --out /tmp/bundles && VEIL_EMBEDDED_BUNDLES=/tmp/bundles go test ./internal/plugins -run EmbeddedBundlesLive -v` in `apps/backend` hits the live sites and compares every plugin's list/find output with Bun's (xhamster's tag order varies per request).

Plugins may send the site's own `rating` (0..10) and `view_count` on `Scene` and on listing `DiscoveredItem`s; cards show them. Only eporner does so far.

**Type mirrors — keep in sync in one commit:** `apps/backend/internal/plugins/types.go` ⇄ `packages/veil-sdk/src/types.ts`.

**Capabilities:** `meta`, `discover`, `scrape`, `search`, `enrich`, `resolve` (embed/page URL → playable mp4/HLS + headers; `meta.domains` routes, `"*"` = wildcard), `browse:categories`, `browse:actors`, `scene:list:page` (`scene:list` with a `url` arg lists a channel/performer/category page; eporner, hqporner), `cam:list` (rooms online now: args query/tag/gender/limit/offset, returns `CamRoom`s + total) and `cam:stream` (room username → live HLS master as a `ResolveResult`), `face:identify` (see Face identification).

**Protocol** (stdin/stdout JSON): `{ "capability", "args" }` in, `{ "result" } | { "error" }` out — except `scrape`, which streams NDJSON: one `ScrapeResult` per line, root entity (scene/gallery/image/collection) first, then related standalone entities (performer/studio/tag). A list may write `{ "items": [...] }` lines before its result so live search shows them while it keeps crawling (SDK `ItemSink` for page crawls, `emitItems` for site fan-outs; spankbang, kvs, aylo do); the result still carries every item and `Runner.ListStream` forwards each item once.

- `Scene.studio` is a structured `StudioRef { name, external_id?, source_url? }`.
- Plugins may emit `Collection` with ordered `member_urls`; unresolved members are auto-queued for scraping.
- Plugins may emit `Scene.markers` (tag/label + seconds/end_seconds) — ingested as global markers.
- `scene:find` should fill `Scene.related` with the page's related-videos list as `DiscoveredItem`s, using the same external_id scheme as the plugin's listings (reuse the listing card parser).

**FlareSolverr:** set `meta.requires_solver: true` when the site answers plain requests with a Cloudflare challenge, and fetch through `fetchHtmlSmart`. Without `FLARESOLVERR_URL` (e.g. embedded on a phone) the registry treats such plugins as unavailable: they drop out of search/browse, their stubs are hidden, visits skip them. Currently: missav, spankbang.

**Expiring media:** set `meta.expiring_media: true` when the site signs poster/preview URLs with an expiry (sxyprn: valid until the next full hour). `internal/mediakeep` then copies each listed stub's poster into `posters/` in the background (unless it is already a blob or comes from another site) and swaps in the listing's fresh `preview_video` whenever the scene is listed again; stubs whose URL had already expired are repaired the next time a listing shows them. Preview clips are not copied, so an old stub's clip only works after it is listed again.

**Current plugins:** aylo (pornhub, redtube, youporn, tube8), eporner (API + enrich), hqporner, kvs (37 Kernel Video Sharing sites from one config list), missav, xhamster, spankbang, tnaflix, txxx-network (scenes); pornpics (galleries); pornstarbyface, facedigger (`face:identify` only); chaturbate (live cams: `/api/ts/roomlist/room-list/` and `get_edge_hls_url_ajax`, both need the `X-Requested-With: XMLHttpRequest` header). Stripchat is not supported: its room list is open but its HLS playlists are gated by Mouflon and serve only an ad loop without the player's key.

## Cams

A cam model is a live room, not a scene: it comes and goes. Cam plugins (`cam:list`, `cam:stream`; see Plugin system) never produce scenes, so none of the scene discovery, ingest or recommendation code sees them.

- `cam_model` (id `cam_model:<id>`, identity `source_url`) stores every room a listing has shown: name, thumbnail, tags, gender, subject, viewers, `online`, `last_seen_online_at`, and the `followed` flag. Rows are upserted whenever a listing page is fetched, so followed rooms stay known while offline.
- `camRooms(sources, tag, query, gender, limit, offset)` lists live to the plugins on request (`internal/cams`): each plugin is paged in chunks of 100, chunks are cached in memory for 60 s so paging stays stable, plugins keep their own popularity order and are merged by viewers. Rooms in a private or password show are skipped. `camSources` feeds the site filter.
- Online status of one room (`camModel`) or the Following row (`followedCamModels`, online first) is a `cam:stream` probe, reused for 45 s. `followCamModel` / `unfollowCamModel` flip the flag.
- `camStream(id)` resolves the room and returns a proxy URL from `Proxy.LiveManifestURL`: a live session, so playlists are fetched fresh, LL-HLS tags (parts, preload hints, blocking reload) are stripped, and segments are relayed without writing the blob store or kv cache. The site's token URL expires within about a minute, so the player asks for a stream right before loading it and again on retry.
- Recording: `Recorder` (`internal/cams/recorder.go`) pulls a room's HLS stream in the backend, so a capture outlives the page. `startCamRecording(id, quality)` picks the rendition from the master playlist (`quality` = `source`, the best, or a target height like `480`: the tallest at or below it, else the shortest above; `chooseVariant`), and re-resolves the stream and re-picks on every reconnect, since token URLs expire within about a minute and renditions change. The video playlist is followed with its separate audio rendition when the master has one (Chaturbate does), and each segment is stored once (deduplicated by URL path, discontinuity marked after a gap). A capture ends on `stopCamRecording`, when the broadcast ends, after `offlineGrace` (90 s) without a reachable stream, or after the `camRecordingMaxMinutes` setting (default 240 min). Footage under 5 s is dropped.
- Where recordings live: `recordings/<id>/` in the blob store (`index.m3u8`, `seg-NNNNN.ts|m4s`, `init-N.mp4`, and with separate audio `video.m3u8`, `audio.m3u8`, `aseg-*`, `ainit-*`, `poster.jpg`). The prefix is outside `stream-cache/`/`img-cache/`, so the cache evictor never touches it, and it is encrypted at rest with `BLOB_ENCRYPTION_KEY` like `stream-cache/`. `index.m3u8` is rewritten every 10 segments, so `Recorder.Recover` (at start) files a capture a crash interrupted from the playlist it had flushed. `cam_recording` rows (status `recording|finished|failed`, stop reason, quality, duration, size, scene) keep the history.
- A finished recording is a normal scene: source URL `veil-recording:<id>` (`ingest.RecordingSourcePrefix`, exempt from duplicate merging because two sessions of one model share performer and runtime), title "<name> — live <date time>", the model's performer (found or created by `name_key` through ingest), the cam site as studio, tags "Live cam" plus the room's own, the room thumbnail as poster, `detail_fetched_at` set, and one stream (format `hls`) pointing at `index.m3u8`. `stream.CacheService.IsRecording` keeps `Resolve`/`ManifestURL` from copying it into the stream cache; it plays straight from the blob store. `downloadedScenes` (Downloads) lists recordings with the completed downloads, newest first.
- `camRecordings(camModelId, activeOnly)` returns the running recordings (live duration, size, quality) then finished ones; `setCamAutoRecord(id, enabled, quality)` stores `cam_model.auto_record` and `record_quality` (turning it on also follows; unfollowing turns it off). `AutoRecorder` polls followed auto-record models every 2 minutes through the cached online probe, staggered, and starts a recording at the model's quality when she is live and none runs for her; one room never has two captures.
- Rewind buffer (`internal/livebuffer`): while a room is watched (`camStream` sessions carry the room id, `Proxy.SetLiveBuffer`) or recorded, the segments of every rendition the player fetches (video, and the separate audio playlist) are kept for the last 180 s (`WindowSeconds`) as blobs under `live-buffer/<cam id>/` (outside the cache prefixes, so the evictor ignores them; encrypted like recordings). Metadata only is in memory. The playlist the player gets is that window as a sliding live playlist carrying the origin's sequence numbers (renditions stay aligned for ABR switches), with a discontinuity wherever segments were missed (reconnect, gap) and `#EXT-X-ENDLIST` once the origin ends; segments are downloaded once by a small worker pool (newest first, the one a player asks for jumps the queue) and served from disk, falling back to the origin. A rendition keeps only what was fetched since it was first played; the player can rewind within its window, not before watching began. A room's buffer is dropped 2 min after the last viewer playlist/segment request or recorder poll (and a rendition 2 min after its last playlist), all buffers at startup. The recorder shows its polls to a room's buffer that already exists (never creates one) and reads segments the buffer holds instead of fetching them again.
- Record from the past: `startCamRecording(id, quality, fromSecondsAgo)` seeds the recording with that much of the buffer (whole segments, capped to what is buffered, nothing when the room is not buffered), then goes on live in the same recording and scene. The recording continues in the buffered rendition (`quality` is ignored for it; the quality label says which), and a break is marked when the buffer's last segment is gone from the live playlist. Web: the live player has a rewind bar over hls.js's playlist range (seek back up to 3 min, "-m:ss" next to Live), and the Record menu offers "From here" (at the playhead when behind live), "From 1 min ago" and "From 3 min ago" when that much is buffered.
- Web: Cams in the sidebar and phone drawer, `/cams` (live grid with `ScrollSentinel`, search, gender and site filters, tag filter via `?tag=`, Following row, a "Recording" strip and REC/Auto badges on cards) and `/cams/[id]` (the scene player `VideoPlayer` in `live` mode: LIVE badge and "Go live", no seek bar, speed, markers or progress saving; quality menu from the hls levels, last pick in `localStorage` `veil.cam.quality`; unmuted start with a "Tap to unmute" prompt when the browser refuses; a stream error asks for a fresh URL up to 3 times before the offline state), Record button with a quality menu, follow, auto-record toggle and quality, and the finished recordings as `SceneCard`s. `ActiveRecordings` lists running recordings (avatar, name, pulsing dot, time, quality, Stop) in the sidebar and drawer, polled every 10 s by `stores/camRecordings.ts`.
- Android (`ui/cams`): Cams in the gear menu and the Library hub, followed rooms on the Following tab. `CamsScreen` (route `cams?tag=`) is the live grid (search, gender and site chips, tag chip, Recording strip, Followed cams, REC/AUTO badges); `CamRoomScreen` (`cam/{id}`) plays the room in the scene player's live mode (`PlayerExtras.live`: LIVE badge, rewind within the window ExoPlayer gets from the buffer with "-m:ss" and Go live, no frame step, speed or loop), asks for a fresh URL up to 3 times on errors, and has Follow, Record (sheet: start in the past by `recordStarts`, or Source / a stream height), Auto-record with its quality, and the finished recordings. No quality memory across rooms yet.

## Running

```sh
bun dev   # process-compose: plugin bundler (watch) + backend + web native, FlareSolverr via docker compose
```

Backend state lives in `DATA_DIR` (default `apps/backend/data`): `veil.db` + `blobs/` + `plugins/` (bundles). Wipe = stop the backend and delete that directory. `DNS_SERVERS` (comma-separated) or `DNS_SERVERS_FILE` (re-read per lookup) override the resolver where Go can't find the system one (Android). `HOST` sets the bind address (default all interfaces), `PLUGIN_INDEX` the plugin index URL.

Cache blobs (`stream-cache/`, `img-cache/`) are capped at `CACHE_MAX_BYTES` (default 300 MB, `blobcache.DefaultMaxBytes`): once over, the least recently used are evicted down to 90%, checked at start, every 15 min and shortly after writes. Last use is the file's mtime, bumped when served. An HLS stream (manifests + segments) is evicted as one, with its kv entries. Kept and not counted: downloads (blob URLs in download jobs), and streams in playback or being cached (any of their files used in the last 5 min, or during a running cache operation) until they go idle. Other blobs used in the last 5 min are counted but kept. Posters, `images/` and plugin icons are never evicted. Cache files may be deleted by hand: lookups check the blob (and every segment of an HLS stream) exists and otherwise go back to the origin; at start, kv entries for missing blobs are dropped, downloads whose file is gone are marked failed, and half-written `.put-*` files are removed.

**Search lab** (in `apps/backend`): `searchlab/queries.json` lists the queries (easy to hard) and plugins. `go run ./cmd/search-lab fetch` (with `FLARESOLVERR_URL` for missav) runs them through the installed bundles in `data/plugins` and freezes the results in `searchlab/snapshot.json`, keeping existing grades; `go run ./cmd/search-lab label` serves a grading page on 127.0.0.1:8099 (0 wrong, 1 loose, 2 fits, 3 exactly it; keys 0–3), saved to `searchlab/labels.tsv`, which can also be edited by hand; `go run ./cmd/search-lab eval` scores every theory in `internal/searchlab/theories.go` (nDCG@10/24, P@10) and compares each site list's labelled precision with its list fit. A new idea is a new `Theory` there.

## Code style

Readability and maintainability over cleverness. Match the surrounding code when it conflicts with the rules below.

- Give every function a doc comment saying what it does, so it reads clearly at the call site (`// Name …` in Go, `/** … */` in TS). The signature carries the types — don't restate them in `@param`/`@returns` tags.
- Comments are technical, concise, and for the reader who arrives later. Add them where skimming the code isn't enough — not to restate it. Don't document a feature you just removed.
  - Good: `// Normalize external IDs before database lookup.`
  - Bad: `// Now we loop through the items and do the thing.`
- Descriptive names, never shortened. `camelCase` for variables, functions, parameters and object fields unless the language or the existing code says otherwise.
  - Good: `recordId`, `customerAccount`, `paymentMethod`
  - Bad: `rid`, `acct`, `pm`
- Explicit control flow over shorthand. Avoid `??`, ternaries and compact conditionals unless they clearly save a lot of repetition.
  - Good: `if (timeout === undefined) { timeout = DEFAULT_TIMEOUT }`
  - Bad: `const timeout = options.timeout ?? DEFAULT_TIMEOUT`
- Svelte: use its directives for dynamic classes (`class:rotate-0={open}`) over string-building (`class={open ? "rotate-0" : "rotate-90"}`).
- Don't declare a variable that's used once; use the expression inline.
- More than 2 levels of nesting is too much — use guard clauses, early returns, or extracted helpers.
- Short, focused functions, one responsibility each. Prefer a named helper over long inline logic with a comment above it.
- Don't change behaviour, public APIs, data shapes, validation or side effects unless asked.

## Tests

When your changes are written, consider whether they need a test, and add one next to the code it covers:

- Go: `*_test.go` beside the package, run `go test ./...` in `apps/backend`.
- Plugins: `tests/*.test.ts` in the plugin, run `bun test` there.
- Browser flows: Playwright, run `bunx playwright test`.

Failures mean investigate, not move on.
